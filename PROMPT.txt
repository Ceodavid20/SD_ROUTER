# 5. SNMP MONITORING ENGINE

This is a critical component.

The application must use SNMP to collect interface traffic information from registered MikroTik routers.

IMPORTANT:

WE ONLY WANT TO MONITOR TX (TRANSMITTED/OUTBOUND TRAFFIC).

DO NOT INCLUDE RX IN THE CURRENT MATHEMATICAL MODEL, DATABASE METRICS, GRAPHS, OR OPTIMIZATION ENGINE.

The application should read the appropriate SNMP interface counters, preferably 64-bit outbound octet counters where supported.

Use the correct SNMP OIDs for the selected interface.

The monitoring process must:

1. Connect to each registered router.
2. Identify the configured interface.
3. Read the current TX octet counter.
4. Record the timestamp.
5. Compare it with the previous counter reading.
6. Calculate the amount of transmitted data.
7. Calculate TX bandwidth in Mbps.
8. Save the measurement.
9. Repeat after one minute.

Use this bandwidth formula:

TX Mbps = ((Current TX Octets - Previous TX Octets) * 8) / (Elapsed Seconds * 1,000,000)

Do not assume the interval is always exactly 60 seconds. Calculate using actual elapsed time.

Handle:
- SNMP timeouts
- Router disconnections
- Interface resets
- Counter resets
- Counter wraparound
- Missing previous readings
- Invalid interface indexes
- SNMP authentication errors

Do not generate fake measurements in production mode.

Provide a simulation mode for development and testing.

The monitoring service must work independently of the web request lifecycle.

Use a scheduler or background service to run the monitoring cycle every 60 seconds.

Avoid starting multiple duplicate schedulers when Flask reloads or runs multiple workers.

# 6. MATHEMATICAL PROCESSING ENGINE

Create an independent mathematics service.

It must implement the following processing stages:

A. READ

Collect the TX measurements obtained from SNMP.

B. MULTIPLY

Provide a configurable multiplication operation.

The exact multiplication formula has not yet been confirmed by the network supervisor.

Do not invent a permanent formula.

Design the module so the formula can be changed easily after confirmation.

One possible working hypothesis is:

Traffic Financial Cost = Traffic Volume × Financial Cost per Unit

Clearly label this as a provisional assumption.

Ensure that measurement units are consistent. If traffic is measured in Mbps but the price is per MB, perform the appropriate time and unit conversion.

C. NORMALIZE

Implement a configurable normalization service.

One possible working formula is:

N_i = BW_i / SUM(BW_i)

Where:
- N_i is the normalized value for router i.
- BW_i is its TX bandwidth.
- SUM(BW_i) is the total TX bandwidth across monitored routers.

The normalized results should be proportions between 0 and 1 when the total is positive.

Handle zero total bandwidth safely.

The exact normalization formula must remain configurable until confirmed by the supervisor.

D. AVERAGE (AV)

Calculate the five-minute moving average using the most recent five one-minute TX bandwidth readings.

Formula:

AV = (BW1 + BW2 + BW3 + BW4 + BW5) / 5

Calculate the average independently for each monitored router/interface.

Use a rolling window.

For example:
- Minute 1: collect reading 1.
- Minute 2: collect reading 2.
- Minute 3: collect reading 3.
- Minute 4: collect reading 4.
- Minute 5: calculate the first average.
- Minute 6: discard the oldest reading, add the latest reading, and recalculate.

Do not calculate a complete five-reading average until five valid readings are available.

E. PREVIOUS AVERAGE (PAV)

Store the previous calculated five-minute average.

When a new AV becomes available:

- Retrieve the previously stored AV.
- Assign it to PAV.
- Store the new AV for the next comparison.

Handle the initial state where no PAV exists.

F. PERCENTAGE CHANGE (DELTA %)

Implement:

DELTA % = ((AV - PAV) / PAV) * 100

Interpretation:
- Positive result: traffic increased.
- Negative result: traffic decreased.
- Zero: traffic remained unchanged.

Handle PAV = 0 without division errors.

G. WRITE

Store processed results in the database.

Prepare the appropriate JSON configuration output after the optimization engine has generated a valid decision.

Keep the mathematical processing engine separate from the SNMP service, optimization engine, and router communication service.

IMPORTANT:

The mathematical operations must be configurable because the supervisor's exact multiplication and normalization formulas have not yet been confirmed.

Do not silently substitute your own interpretation.

# 7. FINANCIAL OPTIMIZATION ENGINE

Create a separate optimization module.

The primary objective is to minimize the total financial cost of transmitted traffic.

Use this initial mathematical model:

Minimize:

Z = SUM(c_i * x_i)

Subject to:

SUM(x_i) = D

0 <= x_i <= C_i

Where:

- Z = Total financial cost.
- c_i = Financial cost per unit of traffic through router i.
- x_i = Traffic allocated to router i.
- D = Total outbound traffic demand to distribute.
- C_i = Maximum available capacity of router i.

Use a linear programming solver such as SciPy's linprog where appropriate.

The optimization engine must:

1. Read current TX traffic.
2. Read each router's available capacity.
3. Read each router's financial unit cost.
4. Determine total traffic demand.
5. Calculate the lowest-cost feasible allocation.
6. Respect router capacity limits.
7. Return the recommended traffic allocation.
8. Calculate the expected financial cost.
9. Explain why the allocation was selected.

IMPORTANT DESIGN CONSIDERATIONS:

- Do not confuse routing cost/metric with financial cost.
- They are different values.
- Do not assume changing an OSPF metric produces an exact traffic percentage.
- Routing protocols may not distribute traffic according to the mathematical allocation.
- Consider ECMP, policy-based routing, and other appropriate mechanisms only after checking the actual network topology and routing protocol.
- Do not make automatic routing changes until the configuration method is confirmed and tested.

The optimization engine should be able to work with simulated data before being connected to real routers.
