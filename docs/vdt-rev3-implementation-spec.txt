2. Architecture and security boundary

Flask makes decisions; MikroTik fetches and executes them.

Production flow:
  approved independent measurements -> durable database -> scheduled decision
  -> mode/approval release gate -> authenticated cost JSON -> router-initiated
  fetch/validation -> separately authorized router-local OSPF application
  -> router readback/report -> database, NOC pages and alerts.

Flask never logs in to production routers, modifies router configuration, sends
remote commands or embeds executable RouterOS code in a decision. Existing
private operator/bootstrap tools are separate from the serving application.
One-time trusted bootstrap/installation still needs initial network connectivity
and explicit trust authorization. Enrollment does not grant execution permission.

The official requirement is stricter than the present lab: no RouterOS login
passwords on the production server. Current API-SSL sampler/diagnostics use
private login credentials and are not the production collection solution.
Do not delete or disable the functioning lab while replacing that dependency.

Production measurement method is NOT YET DECIDED. Candidate designs to assess:
  - authenticated, timestamped, replay-protected router-pushed TX counters, plus
    approved timing probes that traverse the actual monitored link;
  - independently scheduled read-only SNMP counter collection, plus equivalent
    path-specific timing probes, without RouterOS login credentials.
SNMP security credentials or device HMAC keys are not RouterOS login passwords;
they remain protected secrets. Neither candidate is approved by this baseline.
Measurements must not depend on PRTG, SolarWinds or InterMapper availability.
Never collect RX counters under the current user-authorized scope.

Keep verified HTTPS and existing HMAC-SHA512, closed JSON schemas, finite/ranged
numbers, timestamp/expiry checks, rate limits and durable replay protection.
Source-address restrictions supplement authenticated identity; neither replaces
the other. Configure exact production router management addresses and trusted
proxy handling, reject unexpected sources, and expose neither service publicly.
The dashboard is for individually named authorized staff on the NOC/VPN network.
No secrets in registry JSON, HTML, history, readiness reports or log messages.

4. Measurement and decision contract

Official schedule: independently scheduled checks at configurable 5, 10 or
15 minute intervals. Routers fetch released costs about every 60 seconds.
These are separate clocks. A fetch reads the latest release; it must not create
an extra decision or count as another congestion-confirmation check.
The existing one-second lab graph is a separate presentation/collection feature.
Do not silently reset it when introducing the production schedule.

Outbound Mbps = (new TX octets - previous TX octets) * 8 / elapsed_seconds / 1e6.
Use real elapsed time, same router/interface/counter generation. The first
sample, reset, out-of-order counter or invalid elapsed time cannot yield a valid
rate. Capacity must be positive and confirmed before utilization is calculated.
Record raw sample provenance, observation/receipt times, validity and units.

Latency and jitter must be measured independently from TX. Define the probe
direction, endpoints, statistic, sample count and loss handling with the chosen
measurement method. Existing lab jitter is successive successful RTT variation;
do not label it one-way jitter or invent network jitter from Mbps fluctuations.
The path must traverse the link, not merely test management-LAN reachability.

A valid check is congested if any approved metric crosses its threshold. It is
healthy only when all required metrics are valid and within limits. Missing,
stale, partial or failed data is unknown, not healthy or zero. Proposed safety
behavior: unknown breaks consecutive confirmation and blocks cost adjustment;
continue recording and alerting. Freeze this detail in policy tests before use.
Freshness/expiry must fit the approved 5/10/15-minute schedule; do not reuse the
lab's short staleness windows blindly. Monotonic scheduling avoids duplicate
checks; UTC timestamps and policy/check IDs make restart/replay deduplication
durable. No catch-up burst may count old data as new confirmations.

The official policy requires two consecutive scheduled congested checks, or
two consecutive healthy checks, before reacting. One congested and one healthy
link permit a small preference shift toward the healthy link.
Official default step bands: capacity difference under 10% -> 1%; 10–30% -> 5%;
over 30% -> 10%. Step sizes must be editable from Settings.
The capacity-difference denominator, reference cost for the percentage step and
integer rounding are undefined by the supplied plan. Keep these as explicit
choices; do not silently implement one as an approved rule. Any eventual rounding
must ensure a bounded meaningful integer step, without overshoot or endless
adjustment attempts at a limit. Normal recovery must not cross normal cost.

Proposed implementation: a pure deterministic policy module consuming a frozen
settings version, a pair of validated checks and prior confirmation/cost state.
It produces bounded proposed costs, reason codes and evidence references.
Record one decision per scheduled check and policy version, including no-change
decisions. Exact step math awaits the decisions above. Existing MLU and PCC
weights must not be presented as the official OSPF step algorithm.

5. Calculated, released and applied costs

Calculated: the policy's proposal and reasons, retained even when not released.
Released: the approved version the router is allowed to fetch.
Applied: the router's validated readback/report of its actual configured cost,
with identity, resource, time, release version and success/failure details.
Unknown application stays unknown. V1/V2 receipt ACKs keep their existing meaning.

Test: calculate and record proposals, always publish approved normal costs.
Manual: record proposals; release only the exact proposal explicitly approved
by an authorized staff account. Proposed approvals bind settings/measurement
versions, expire on stale evidence, and cannot authorize a newer proposal.
Automatic: release fresh bounded proposals only after staged authorization.
Mode changes, approvals and release versions must be transactional and audited.

The current Optimization On/Off switch remains a separate lab advisory pause.
It cannot silently become production Test/Manual/Automatic or a restore command.
Entering Test immediately changes the server's release to normal; the router
can restore only after its next successful fetch and verified application.
Do not promise instant router rollback if the router cannot contact the server.
The outage policy is CTO's choice: hold last (document's recommended default),
or restore approved normal after N failed pulls. Neither is selected yet.

Router-local routine (a later authorized stage): fetch only its own release,
verify TLS/controller trust, HMAC, identity/resource scope, strict numeric types,
signature, time/expiry/version/replay and approved bounds. Reject executable
content, unknown resources or invalid values. Apply only a changed value to
the approved OSPF resource; read back and report. Duplicate polls are idempotent.
Validate scoped template matches so one target cannot alter unrelated links.
Persist the validated release/application state needed across router restarts.
An authenticated report is still router-reported evidence, not independent proof
that customer traffic moved. Exercise physical hardware before claiming support.

RouterOS reference for template scope/cost (consulted 25 November 2026):
https://manual.mikrotik.com/docs/cli-reference/routing/ospf/interface-template/
https://help.mikrotik.com/docs/spaces/ROS/pages/9863229/OSPF
Actual version capabilities and operator-approved min/max bounds must both pass.

7. Operations, alerts and rollout

Raise deduplicated alerts for measurement failure, missing router cost fetches,
and applied/released mismatch beyond an agreed delay. Record recovery, age,
delivery attempts and acknowledgement. Recipients/channel and timings need
operator settings. Never send external messages as part of Stage 1.

Target deployment: private-management/VPN-only Ubuntu cloud server, 2 CPU,
4 GB RAM, 40 GB persistent storage, supervised workers/proxy, synchronized
time, separate daily backups, tested restore, retention/log rotation and regular
security updates. Validate performance at the intended production workload.
Record named accounts, least privilege and operational ownership in the runbook.

Keep software build stages distinct from official operational rollout:
  Lab test: spare/isolated router, validate every router-local guard and OSPF
    readback without customer traffic.
  Test: at least the prescribed 1–2-week observation period; start/end and review
    recorded, real check-ins but normal released costs, proposals only recorded.
  Review: Busuyi, CTO and DSA assess decisions against real conditions.
  Manual: first live weeks, each released change explicitly approved.
  Automatic: only after acceptance/sign-off, within bounds and ongoing oversight.
Document emergency Test restore, router-local pause/manual restore and outage
behavior before live use. No silent mode promotion by elapsed time alone.

Real congestion-relief proof needs traffic through the common forwarding path
able to use either link, with before/after measurements and verified OSPF cost
application. Generating TX directly toward carrier-connected test addresses
shows monitoring and advisory calculation, not OSPF-driven traffic movement.

9. Stage 1 command and completion boundary

Run: .venv/bin/python manage.py rev3-readiness
JSON: .venv/bin/python manage.py rev3-readiness --json
Optional --decisions PATH selects a validated planning register, not live policy.
The assessor reads only an existing consistent JSON inventory/settings snapshot
under a shared lock. It never initializes a profile, contacts a router, resolves
API credentials, recovers storage or writes settings/history. Reports expose
counts and whitelisted decisions, not router addresses, credentials or references.
Uninitialized/unavailable inventory is reported, not created or repaired.

Stage 1 software deliverables can be complete while decisions remain pending.
Even a fully completed register cannot grant production readiness or router
execution authorization. The assessor is an inventory/planning aid, not an
application mode gate, rollout approval system or proof of physical operation.
Proceed with isolated Stage 2 preparation without disturbing the live lab;
The database decision is now recorded; see docs/vdt-rev3-database.txt for Stage 2
staging, real database checks and the separate runtime cutover boundary.
