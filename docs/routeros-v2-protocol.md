# RouterOS polling protocol v2

The device-only app accepts `POST /api/controller/v2/poll` and
`POST /api/controller/v2/ack`. The browser app exposes neither path.
Version 1 is unchanged and documented separately in
[the Python v1 reference](router-pull.md).

## Requests and authentication

Use `Content-Type: application/json`, no query parameters or
`Content-Encoding`, and at most 8192 UTF-8 bytes. A poll has exactly:

| Field | Required value/type |
| --- | --- |
| `protocol_version` | String `"2.0"`. |
| `router_id` | Exact authorized registry ID; 1–64 letters/digits/underscore/hyphen, first character alphanumeric. |
| `request_id` | Fresh canonical lowercase UUID4. |
| `timestamp` | Positive integer Unix UTC seconds; not a float, string or boolean. |
| `request_type` | String `"poll"`. |

An ACK changes `request_type` to `"ack"`, uses a new UUID4 and current
timestamp, and adds `response_id`: the UUID4 of the validated poll reply.
Duplicate, extra, missing or wrongly typed JSON properties are rejected.

Headers are `X-SDR-Key-Id` and `X-SDR-Signature`. The signature is 128
lowercase hexadecimal characters. Sign these five ASCII lines, with
literal newline separators and **no trailing newline**:

```text
SDR-POLL-V2
POST
/api/controller/v2/poll
KEY_ID
LOWERCASE_SHA512_HEX_OF_EXACT_RAW_BODY
```

For an ACK, sign `/api/controller/v2/ack` in the third line. The digest
and HMAC must use the exact transmitted bytes; JSON property order is
irrelevant only when the signer and sender use the same raw body.
Compute standard HMAC-SHA512 using the secret's UTF-8/ASCII bytes.
The generated 64-character hexadecimal secret is **not hex-decoded**.

Unknown/disabled routers, inactive/revoked keys, invalid signatures and
stale/future timestamps receive generic `401` results. Accepted request
IDs are consumed under the same lock as the accepted check-in update.
Replay protection survives restart through JSON storage. The signed
timestamp remains covered through the inclusive maximum-age boundary.

## Successful replies

A poll returns exactly fourteen fields:

| Field | Meaning |
| --- | --- |
| `protocol_version` | `"2.0"`. |
| `router_id`, `request_id` | Bind the reply to the authenticated router and request. |
| `response_id` | New canonical lowercase UUID4 generated by the server. |
| `status` | `"authenticated"`. |
| `mode`, `action` | `"dry_run"`, `"none"`. |
| `configuration` | Empty JSON object `{}`; no commands or routing changes. |
| `reason` | `"optimization_unavailable"`. |
| `issued_at`, `expires_at` | UTC ISO timestamps at whole seconds, ending in `Z`. |
| `issued_at_unix`, `expires_at_unix` | Exact matching positive integer epoch seconds. |
| `poll_after_seconds` | Configured integer polling delay, 1–86400 seconds. |

Validity is positive and at most 300 seconds. The router validates the
identity, request binding, field count/types, validity, empty-object
configuration and allowed no-action state before acknowledging. It
rejects a response ID already handled during its current process state.
It never evaluates a returned command or script.

A successful ACK response has those fourteen fields plus
`acknowledged_response_id`. Its `status` and `reason` are both
`"receipt_recorded"`; the referenced ID must equal the poll response the
client acknowledged. An ACK authenticates independently and can only
reference that same router's known unexpired response. Unknown, foreign
or expired references return `409`. Fresh authenticated ACK retries for
an already recorded response are idempotent; replaying an accepted ACK
request ID still returns `409`.

Receipt history is tied to specific issued response IDs. A delayed or
duplicate ACK for an older response cannot rewind a newer acknowledged
response's summary, including when polls were issued in the same second.

## Storage and observed status

`data/router_communication_v2.json` stores bounded accepted-request IDs,
unexpired issued-response references, the last authenticated check-in,
and received-response metadata per router. V1's separate communication
state retains the source-rate-limit buckets shared by both protocols.
Each HTTP request counts once, including malformed and rejected attempts.
Routers behind the same NAT source share that source's budget. Plan a
budget of at least two requests per successful exchange per router plus
reasonable headroom; do not disable the limit to mask a retry loop.

The UI distinguishes an authenticated request, an issued reply and a
matching receipt. A new poll does not make a prior response's receipt
apply to the new response. Disabling an identity takes precedence over
an old check-in. API diagnostics remain separate. There is no applied
configuration state because this protocol issues no routing action.

The communication files are validated, locked, backed up and atomically
replaced. Replay and response lists are capped at 10,000 live records
each; capacity exhaustion returns `503` rather than evicting live
protection. Old entries are pruned as requests are accepted. Activity
events contain safe codes, identities and response IDs, not raw bodies,
secrets or authentication headers.

## Transport and errors

Use verified HTTPS and the approved TLS proxy, with the backend bound to
loopback. Untrusted forwarded headers cannot establish HTTPS. Only the
explicit configured local proxy is trusted. HTTP is allowed solely for
loopback simulation when `SIMULATION_MODE=true`; the native client
always requires HTTPS and certificate validation, with redirects off.

| Status | Meaning |
| --- | --- |
| `200` | Authenticated request accepted; inspect the strict reply. |
| `400` | Invalid JSON, schema, encoding or query. |
| `401` | Generic authentication/freshness failure. |
| `403` | HTTPS required or proxy source restriction denied. |
| `404` / `405` | Unknown path or unsupported method. |
| `409` | Replayed request or unknown/expired/foreign ACK reference. |
| `413` / `415` | Body too large or wrong content type. |
| `429` | Source budget exceeded; observe `Retry-After`. |
| `503` | Storage, clock, response validation or bounded capacity unavailable. |

HMAC authenticates requests; TLS authenticates and encrypts the server
exchange. Keep private keys and rendered client scripts out of browser
routes and logs. See [installation](routeros-setup.md) and
[target-release test evidence](routeros-native-notes.md).
